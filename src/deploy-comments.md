* Session 31: Fix — Buy Now was silently wiping unrelated cart items on fulfillment. webhook.ts's handleCheckoutSessionCompleted() called clearCartForUser(userId) unconditionally after every purchase, deleting the buyer's entire persisted cart rather than just what was bought — invisible for a full-cart checkout (everything in the cart was purchased anyway) but a real data-loss bug for the single-item Buy Now path added in Session 30 (a buyer with an unrelated item already in their cart lost it on an unrelated Buy Now purchase, no error surfaced). Fixed by scoping cart-clearing to the productIds actually charged for: new removeCartItemsForUser(userId, productIds) helper in cart.ts replaces the old unconditional clear, fed from the same full.line\_items already used for fulfillment (no second fetch). clearCartForUser removed entirely — confirmed via repo-wide grep as its only caller. Live-tested this session (see the Checkout Sessions/Wire Buy Now updates above) — confirmed fixed for real, not just via code diff.
* Session 31: Real refunds via Stripe Refunds API — refunds.ts's dbResolveRefundClaim no longer scopes by the admin's own userId (real bug: approving a refund silently no-op'd for any claim that wasn't the admin's own account); now gated by id + status='pending' as an idempotency guard, calls stripe().refunds.create() before flipping the claim's status (a failed Stripe call leaves the claim retryable, never falsely approved). New markSingleDownloadRefunded (downloads.ts, per-download-scoped, replacing the now-dead session-scoped markDownloadsRefunded) and clawbackLoyaltyPointsForBuyer (loyalty.ts, unconditional, can go negative — a clawback isn't a voluntary redemption) wired into the approval path alongside the existing voidAffiliateLedgerForDownload. Also fixed a second real bug caught during this work: the old approval flow credited loyalty points back to the admin's own account instead of the buyer's, via a caller-session-scoped helper being reused server-side. RefundClaimsManager.tsx's approve action now only calls approveRefundClaim; the "restore points" toggle was removed since it no longer controlled anything real. Not yet live-tested — pushed but the five live-sandbox verification tests (partial refund, retry/idempotency, cross-buyer approval, negative-balance clawback, reject-path no-op) haven't been run yet.

* Session 50: Wired Sign in with Apple into the existing Better Auth setup — apple() social provider in auth.ts, fully opt-in on APPLE\_CLIENT\_ID/APPLE\_TEAM\_ID/APPLE\_KEY\_ID/APPLE\_PRIVATE\_KEY (all four required together once APPLE\_CLIENT\_ID is set, otherwise the button just doesn't render), client secret generated via Better Auth's documented generateAppleClientSecret JWT helper rather than hand-signed. Button added to AdminLogin.tsx (the app's only sign-in/sign-up UI) styled per Apple's HIG (official black mark); admin.tsx gained a small ?appleAuth=1 bridge on the OAuth callbackURL since the full-page redirect back can't call the existing sessionStorage-gate handler in memory the way the password path does. Confirmed against better-auth's own source (not assumed) that the anonymous-to-real-user onLinkAccount merge fires for Apple the same as email/password (its hook matches any /callback path, provider-agnostic), and that the OAuth flow has real CSRF/state protection — a random state value stored server-side plus a signed cookie, both cross-checked at callback, same mechanism for every social provider. Not click-tested: Apple Sign In has no localhost/non-HTTPS support at all, so this is verified against source/config only, pending a real run on a Vercel preview URL. A partial/incomplete Apple env-var set no longer crashes the app at boot (initial implementation did; fixed same session) — it now logs which var(s) are missing and disables Apple sign-in only, leaving every other route unaffected.
